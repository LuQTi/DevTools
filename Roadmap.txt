### 💡 Und dann gibt es noch eine Kategorie, die ich besonders interessant finde:

## 🧠 „Developer Helpers“

Tools, die nicht einfach Daten umwandeln, sondern dir **Arbeit abnehmen**.

Zum Beispiel:

**„Ich habe diese cURL-Anfrage“**

```bash
curl -X POST https://api.example.com/users \
  -H "Content-Type: application/json" \
  -d '{"name":"Max"}'
```

→ automatisch:

```javascript
fetch("https://api.example.com/users", {
    method: "POST",
    headers: {
        "Content-Type": "application/json"
    },
    body: JSON.stringify({
        name: "Max"
    })
});
```

Oder:

```text
JSON
 ↓
Java Class
 ↓
PHP Class
 ↓
TypeScript Interface
```

Oder:

```text
SQL
 ↓
erkennt Tabellen
 ↓
erstellt Schema-Diagramm
```

Oder:

```text
Stack Trace
 ↓
erkennt Exception
 ↓
zeigt relevante Zeile
 ↓
erklärt wahrscheinliche Ursache
```

Das sind die Funktionen, die aus einer **„Tool-Sammlung“** irgendwann eine **wirklich interessante Entwickler-App** machen.

GEMEINSAMES SYSTEM:

shared/tool.css
→ enthält das komplette gemeinsame Design aller Tool-Seiten.

shared/tool.js
→ enthält gemeinsames Verhalten:
- Dark/Light Mode
- Theme aus localStorage
- Zurück zur Startseite
- Copy-to-Clipboard
- Statusmeldungen
- gemeinsame Helper

Jedes Tool besitzt KEIN eigenes CSS.

Ein Tool besteht grundsätzlich nur aus:

tools/NAME/
├── NAME.html
└── NAME.js

Die HTML-Datei lädt:

<link rel="stylesheet" href="../../shared/tool.css">

<script src="../../shared/tool.js"></script>
<script src="NAME.js"></script>

Das Design soll bei allen Tools gleich bleiben.

============================================================
1. PROJEKT
============================================================

Wir entwickeln eine Sammlung von kleinen, eigenständigen Developer-Tools.

Das Projekt besteht aus verschiedenen Kategorien:

1. Formatter
2. Encoder
3. Parser
4. Generator
5. Converter
6. Validator

Die Tools werden über eine zentrale Tool-Registry registriert und anschließend dynamisch geladen.

Das Projekt soll sauber, übersichtlich, konsistent und langfristig erweiterbar sein.

Alle Tools sollen sich optisch und strukturell wie Teile derselben Anwendung anfühlen.

5. ZENTRALE REGISTRY
============================================================

Die zentrale Datei ist:

tools.js

Sie enthält:

const CATEGORIES = { ... };

Jedes Tool besitzt grundsätzlich diese Struktur:

toolName: {

    name: "Tool Name",

    description:
        "Kurze Beschreibung.",

    icon: "...",

    category: "categoryName",

    tags:
        "relevante suchbegriffe",

    script:
        "category/tool-file.js",

    comingSoon: false

}

Beispiel:

jsonValidator: {

    name: "JSON Validator",

    description:
        "JSON prüfen und Syntaxfehler verständlich anzeigen.",

    icon: "{}",

    category: "validators",

    tags:
        "json validator validate syntax error api data",

    script:
        "validators/json-validator.js",

    comingSoon: false

}

============================================================
6. REGELN FÜR tools.js
============================================================

Die Registry soll konsistent bleiben.

Bei neuen Tools:

- name muss eindeutig sein
- description kurz und verständlich
- icon passend zum Tool
- category muss einer bestehenden Kategorie entsprechen
- tags müssen relevante Suchbegriffe enthalten
- script muss exakt zum tatsächlichen Dateipfad passen
- comingSoon ist false, wenn das Tool fertig ist

Keine unnötigen Tags.

Tags sollen echte Suchbegriffe sein, die ein Benutzer erwarten könnte.

Beispiel:

"json validator validate syntax error api data"

statt völlig irrelevanter Begriffe.

Bei Änderungen an tags immer auf:
- deutsche und englische Begriffe, wenn sinnvoll
- Fachbegriffe
- typische Synonyme
- Suchintention
- keine redundanten oder sinnlosen Wörter

achten.

============================================================
15. TOOL-FUNKTIONALITÄT
============================================================

Tools sollen nicht nur optisch funktionieren.

Sie sollen:

- echte Eingaben verarbeiten
- Fehler erkennen
- verständliche Fehlermeldungen liefern
- Ergebnisse sauber darstellen
- keine unnötigen Abstürze verursachen
- Edge Cases berücksichtigen
- möglichst mit nativen Browser-APIs arbeiten, wenn diese ausreichen

Bei Validatoren ist besonders wichtig:

Ein Validator soll nicht nur sagen:

"Ungültig"

sondern möglichst erklären:

- warum ungültig
- welcher Fehler aufgetreten ist
- wenn möglich Position/Zeile/Spalte
- relevante Eingabeinformationen

Parser:
    analysiert und zerlegt Daten.

Validator:
    prüft, ob etwas gültig ist.

Ein Validator darf zusätzlich strukturierte Informationen anzeigen, aber seine Hauptaufgabe ist die Validierung.

============================================================
26. SICHERHEIT
============================================================

Bei Tools wie JWT:

JWT kann dekodiert/analysiert werden, weil Header und Payload normalerweise nur Base64URL-kodiert sind.

"Decodieren" bedeutet NICHT automatisch "Signatur validieren".

Ein JWT-Tool darf deshalb klar zwischen:

- Decode
- Inspect
- Encode
- Sign
- Verify

unterscheiden.

Keine falschen Sicherheitsversprechen.
